# 风险与对策

> 关联：[方案总览](/plan/overview) · [系统架构](/plan/architecture) · [路线图](/plan/roadmap)

## 1. 风险评级方法

- **概率**：低 / 中 / 高。
- **影响**：低（体验瑕疵）/ 中（功能受限或延期）/ 高（无法发布、法律风险、数据/设备损坏）。
- **等级**：P1（必须在上线前解决）、P2（需要有明确缓解与监控）、P3（接受并记录）。

风险不是“列出来好看”，而是要有**触发条件**与**可执行预案**。以下每项都对应一个可观察信号。

## 3. 重点风险预案

### R01 NNUE 权重来源与声明

**事实**：项目代码采用 AGPL-3.0-or-later；Pikafish 引擎为 GPL-3.0，可与 AGPL-3.0 组合。NNUE 权重有独立声明，不因代码许可改变。

**影响**：如果核心 npm 包直接携带权重，下游会在不知情的情况下承担额外的分发与使用条件；项目也可能被误解为“权重随代码一起授权”。

**对策**：

1. **核心 npm 包不携带权重**；使用 `netUrl` 或 `netData` 由应用提供。
2. `netData` 随应用打包时，应用需在自身发布物中保留权重来源与声明。
3. 演示站页脚展示权重来源、上游声明与 AGPL 源码入口。
4. 文档不再设置“许可审查”门禁；发布清单只核对来源、声明与源码链接是否齐全。

**预案**：若权重来源或声明变化，更新 `engine.json`、下载入口文案与 `NOTICE`，不阻塞引擎升级。

---

### R03 移动端内存与 OOM

**事实**：网络在内存中约 66 MiB；wasm 初始 64 MiB、线程构建堆上限 1 GiB；Hash 与 pthread 栈另计。iOS Safari 对单标签内存更敏感，超过约 300 MB 的 wasm 分配不可靠。

**触发信号**：页面被系统回收、`RangeError: WebAssembly.Memory`、搜索中途崩溃、切后台回来白屏。

**对策**：

1. 设备探测：`deviceMemory`、`hardwareConcurrency`、UA 兜底；≤ 2 GB 使用单线程，无 SIMD 时用 `single-nosimd`。
2. 单线程构建：无 pthread 池，Hash 默认 16 MB，峰值显著下降。
3. 延迟加载：先渲染棋盘与“开始”按钮，用户点击后再下载网络。
4. 页面隐藏时停止无限分析；对局中只完成当前一步。
5. Hash 上限：移动端 64 MB，桌面 256 MB；超出直接钳制并提示。
6. 压测：iOS 真机连续 20 局，记录内存曲线与页面回收情况。

**预案**：若目标机型仍 OOM，提供“轻量模式”（单线程 + Hash 8 MB + 关闭动画/音效），并在文档标注最低设备要求。

---

### R04 COOP/COEP 与静态托管

**事实**：多线程需要 `SharedArrayBuffer`，它要求页面跨源隔离；GitHub Pages 不能自定义响应头。

**触发信号**：`crossOriginIsolated === false`；`SharedArrayBuffer is not defined`；pthread 创建失败。

**对策**：

1. 运行时探测，自动选择 `single-simd` / `single-nosimd`；功能不缺失。
2. **Vercel 主站**直接设置 COOP/COEP；**GitHub Pages 镜像**用 `coi-serviceworker`：同源加载、首次刷新、SW 注入头；页面明确提示“正在启用多线程”。
3. 文档给出 Vercel/Netlify/Cloudflare Pages/Nginx 的响应头配置。
4. 所有跨源资源带 CORS/CORP，或直接自托管；避免第三方字体/图片。
5. 自动化测试同时覆盖“隔离/非隔离”两种上下文。

**预案**：若 `coi-serviceworker` 在目标浏览器失效，Pages 默认单线程；Vercel 继续提供完整体验。

---

### R05 上游与网络漂移

**事实**：Pikafish 活跃开发；网络是滚动资产（`master-net`），没有稳定 tag；引擎与网络架构必须匹配。

**触发信号**：`NNUE evaluation using ...` 行缺失；初始化失败；同 commit 重建行为不同。

**对策**：

1. `engine.json` 固定：Pikafish commit、patch 哈希、网络 SHA-256、emsdk 版本、构建日期。
2. CI 在每次构建时校验网络 SHA；发布产物附 `SHA256SUMS`。
3. 升级走独立 PR：构建 → 规则回归 → 基准 → 浏览器冒烟 → 更新文档。
4. 保留上一版本产物与网络，支持回滚。
5. 不跟随 master 自动发布。

**预案**：若上游引入破坏性变更，锁定旧 commit 继续维护；补丁保持最小，必要时 fork。

---

### R06 多线程在 Safari/iOS 的稳定性

**触发信号**：pthread 创建超时、搜索无响应、`stop` 后不返回、页面崩溃。

**对策**：

1. 固定 emsdk 版本，记录已知问题；升级前先在 Safari 真机跑完整对局。
2. `Threads` 默认保守（移动端 2），允许用户降到 1。
3. 看门狗：`stop` 后 1 秒无 `bestmove` → 重启 Worker。
4. 单线程构建作为默认可选；Safari 用户可一键切换。
5. 在兼容矩阵中如实标注“Safari 多线程为实验性/稳定”，不隐瞒。

**预案**：若问题无法在发布前解决，Safari 默认单线程，多线程作为“实验性开关”。

---

### R07 长将/长捉裁决

**事实**：官方规则包含复杂的“捉”定义、牵制、循环序列起止、将军计数。完整实现难度高，且不同平台历史裁决不一致。

**触发信号**：官方 39 个棋例通过率低；玩家报告“应该判负却判和”。

**对策**：

1. 规则包独立，按官方《象棋程序竞赛规则》实现，不混入 UI。
2. 黄金测试：39 个棋例 + 自建边界用例；每次改动全量跑。
3. 分阶段：先保证将死/困毙/限着/子力不足；循环裁决先保守判和，再上线完整分类器。
4. UI 显示裁决依据（“三次重复：双方允许循环，判和”），减少争议。
5. 文档明确 v0.1 的规则覆盖范围。

**预案**：若完整分类器延期，v0.1 标注“循环局面暂按和棋处理”，v0.2 补齐；不假装已完全符合规则。

---

### R09 打包器与 Worker 集成

**事实**：Emscripten 生成物不是标准 ESM；pthread worker 需要重新加载主脚本；Vite/Next 对 `importScripts`、`new Worker(new URL(...))` 的处理不同。

**触发信号**：开发环境正常、生产构建 404；多线程时报 “Cannot load script”；wasm MIME 错误。

**对策**：

1. 发布预构建的 `engine.worker.js` + `pikafish.js` + `.wasm`，不要求下游重新编译。
2. 提供三种接入方式：
   - 静态资源目录（推荐）：复制 `assets/`，传 URL；
   - CDN：`wasmUrl/jsUrl/netUrl` 指向 CDN；
   - 打包器：文档给出 Vite `?url` 与 Next `public/` 示例。
3. `mainScriptUrlOrBlob` 显式指向 jsUrl；测试生产构建，不只测 dev。
4. 提供 `workerUrl` 覆盖项，允许宿主自行托管 Worker。
5. 错误信息直接指出“可能是 pthread 主脚本 URL 丢失”。

**预案**：若某框架无法兼容，提供“无打包器”的 `<script>` 示例作为逃生通道。

## 4. 发布门禁（Go / No-Go）

发布 v0.1.0 前必须全部满足：

- [ ] 规则：将死/困毙/限着/子力不足 100%；循环棋例 ≥ 90% 或有明确豁免说明。
- [ ] 浏览器：Chrome/Firefox/Safari/iOS/Android 冒烟通过。
- [ ] 内存：目标设备连续 20 局无 OOM。
- [ ] 性能：达到目标，或有书面偏差与用户提示。
- [ ] 发布信息：npm 包不含权重；LICENSE/NOTICE/构建脚本/源码入口齐全。
- [ ] 安全：无高危依赖；输入校验与 CSP 文档完成。
- [ ] 文档：API、部署、FAQ、限制说明完整。
- [ ] 回滚：上一版本产物可访问；deprecate 流程明确。

任一 P1 未关闭 → 不发布；可将范围降级为“技术预览”，但必须显著标注。

## 5. 终止/转向条件

以下情况出现时，暂停开发并重新评估方向，而不是硬撑：

1. **M1 连续两周无法稳定构建**：转为“单线程优先”，或评估其他引擎（如 ElephantEye）作为备选。
2. **单线程在目标设备 < 150k NPS**：产品定位改为“分析/教学”而非“实时对弈”。
3. **权重来源或上游分发条件发生根本变化**：暂停网络分发，保留引擎与规则能力，等待可替代网络。
4. **维护成本超出单人能力**：进入维护模式，固定版本，只修安全与严重 bug。
5. **上游明确反对 Web 分发**：停止分发，转为文档/研究项目。

> 提前写下“什么时候不做”，比事后找理由更专业。

## 6. 开放问题

1. 是否存在与 Pikafish 架构兼容、体积更小或声明更宽松的象棋网络？棋力损失多少？
2. `master-net` 的更新频率与兼容策略是否有官方说明？
3. Safari/iOS 上 4 线程的实际稳定性如何？是否需要默认 2 线程？
4. GitHub Pages 托管约 50 MB 网络的长期带宽是否可接受？
5. 是否有必要提供 Node.js 构建（服务端分析/批量跑分）？
6. 规则包是否值得独立发布，还是合并进主包？
7. 是否向上游提交 WASM 入口补丁，以减少长期 patch 维护？

## 7. 风险复查节奏

- **每周**：开发例会过一遍 P1/P2 触发信号。
- **每个里程碑结束**：更新登记册、关闭/新增风险。
- **发布前**：Go/No-Go 清单逐项签字。
- **发布后 72 小时**：监控 issue、崩溃报告、性能反馈；必要时回滚。
