# v1.0.0

给出**三种大小的引擎**：官方的 L1=1024（50 MB）、精简的 L1=512（25 MB），以及新增的
L1=256（12.6 MB）。两个包也在这一版第一次发布到 npm。

- 上游 Pikafish：`545c4e3b251afbb94f493c6c5f32549f900e76fd`
- Emscripten：`3.1.74`
- NNUE（`networks` release 提供，`engine.json` 钉死体积与哈希）：

  | 引擎 | 宽度 | 体积 | SHA-256（前 8 位） |
  | --- | --- | --- | --- |
  | `strong` | L1=1024 | 50,241,100 B | `bf398271` |
  | `lite` | L1=512 | 25,136,309 B | `ac223f6d` |
  | `w256` | L1=256 | 12,646,031 B | `316da393` |

- 许可：AGPL-3.0-or-later

## 新增

### 第三档引擎：L1=256（12.6 MB）

`w256` 与 v0.2.0 的精简网出自同一套蒸馏流程，只改特征宽度（上游源码里的
`constexpr IndexType L1`），语料、schedule、导出复核都一样：

- 导出后复核 500 个局面逐位精确，同宽引擎再复核 4,000 个局面，worst |delta| = 0
- 300 局固定节点对局（4000 节点/步）比教师弱 **−220 Elo**

### 浏览器侧的宽度下限是 12.6 MB，不是 3.2 MB

原生引擎能编 L1=192 / 128 / 64（3.2–9.5 MB），但**浏览器构建编不出来**：上游
`nnue/layers/affine_transform_sparse_input.h` 里，没有 AVX512 时走的那条稀疏输入路径
带 `static_assert(InputDimensions % 256 == 0)`，而 wasm 没有 AVX512。于是 wasm 能编的
宽度只有 256 / 512 / 768 / 1024：

| 宽度 | 原生 | wasm | 说明 |
| --- | --- | --- | --- |
| 1024 | ✓ | ✓ | 官方教师网 |
| 512 | ✓ | ✓ | 精简网 |
| 256 | ✓ | ✓ | **本次新增，浏览器最小** |
| 192 / 128 / 64 | ✓ | ✗ | 稀疏输入层要求 256 的整数倍 |
| 32 | ✗ | ✗ | `ChunkSize * OrderSize must perfectly divide TotalSize` |

所以 `w192` / `w128` / `w64` 没有随本版发布；它们留在 `networks` release 里，只作为
原生对局的测量结果（见下方曲线）。要突破 12.6 MB 只能走标量构建（`single-nosimd`，
约 38 k NPS）或改上游评估结构，两者都不划算：前者把最需要小网的设备拖回深度 15。

### 权重有了固定地址

- 蒸馏网统一放在仓库的 `networks` release，`engine.json` 只钉体积与 SHA-256
- v0.2.0 的 `pikafish-lite.nnue` 也迁到这里，权重地址不再跟着引擎版本 tag 走
- 运行时下载、Cache Storage 与哈希校验的行为不变

### 演示站

- 「引擎 → 网络」选择器列出三套：强力 / 精简 / 轻量（50 / 25 / 12.6 MB），切换时连同
  wasm 一起换（权重只被同宽度的引擎加载）
- 默认仍是精简；`?variant=strong|lite|w256` 可以用链接固定
- 选择器里显示每张网的实际字节数

## 变更

- `scripts/build-wasm.sh` 按 `engine.json` 的引擎表循环，不再写死两套引擎
- CI、Release、Pages 编九套构建（3 套引擎 × 3 种能力）
- 体积守卫的总量预算 7 MB → 8 MB

## 附：宽度 ↔ 棋力（原生引擎实测）

| L1 | 网（zstd） | Elo vs 教师 | wasm |
| --- | --- | --- | --- |
| 1024 | 50.2 MB | 0 | ✓ |
| 512 | 25.1 MB | −158 | ✓ |
| 256 | 12.6 MB | −220 | ✓ |
| 192 | 9.5 MB | −260 | ✗ |
| 128 | 6.4 MB | −284 | ✗ |
| 64 | 3.2 MB | −325 | ✗ |

每减半宽度掉 40–65 Elo（越往下越平：128→64 只掉 41）。这条曲线说明「再小一点」的收益
在 256 之后已经很薄，而 wasm 的编译器约束正好落在那里。
